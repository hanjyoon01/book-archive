# 2장. 느려진 서비스, 어디부터 봐야 할까
## 처리량과 응답 시간
### 성능 지표
- 성능 저하의 현상 : 결과를 늦게 표시 (혹은 타임아웃)
- 성능 지표 : 네트워크 속도, 디스크 속도, 메모리 크기, 디바리스 CPU 속도 등
    - **중요 지표 두 가지 : 응답 시간 & 처리량**
### 응답 시간
- **응답 시간** : 사용자 요청을 처리하는 데 걸리는 시간
    - 사용자가 API를 호출하고, JSON 응답을 받을 때까지 걸리는 시간
- **TTFB (Time To First Byte)** : 첫 바이트가 도착할 때까지 걸리는 시간
- **TTLB (Time To Last Byte)** : 마지막 바이트가 도착할 때까지 걸리는 시간
    - 데이터의 크기가 큼 or 네트워크 속도가 느림 -> TTFB, TTLB 차이가 커짐
    - 데이터 특성, 네트워크 환경을 고려해 적절한 지표를 선택해야 함
- **응답 시간은 길어질수록 서비스에 부정적인 영향을 미침**
- 응답 시간 : API 요청 전송 시간 + **서버 처리 시간** + API 응답 전송 시간
- **서버 처리 시간**
    - 로직 수행 (if, for)
    - **DB 연동 (쿼리 실행) -> 비중 높음**
    - **외부 API 연동 -> 비중 높음**
    - 응답 데이터 생성 및 전송
### 처리량
- **처리량** : 단위 시간당 시스템이 처리하는 작업량
    - **TPS**
    - **RPS**
- **TPS (Transaction Per Second)** : 초당 처리한 트랜잭션의 수
    - **최대 TPS** : 시스템이 처리 가능한 최대 요청 수
    - **동시 요청 수 > 최대 TPS** -> 초과 요청을 나중에 처리
        - 응답 시간이 증가 -> 사용자 이탈로 이어짐
        - 해결 방법 : 동시 요청 처리 수를 증가 or 처리 시간을 감소
- **성능 개선** -> 서버 TPS와 응답 시간을 알아야 함
    - **트래픽이 많은** 시간대의 TPS, 응답 시간
    - 목표 TPS, 응답 시간 설정 -> 개선안 도출
    - TPS 확인 : 모니터링 시스템 (스카우터, 핀포인트, 뉴렐릭)
## 서버 성능 개선 기초
### 병목 지점
- **사용자 수, 트래픽 크기, DB 크기**가 커지면서 성능 문제 발생
- 성능 문제의 증상
    - 순간적으로 모든 사용자 요청 응답 시간이 느려짐
    - 서버 재시작 시 완화 -> 점차 다시 느려짐
    - 트래픽이 줄어들 때까지 문제가 지속됨
- 주요 원인 : **최대 TPS를 초과**하는 트래픽 유입
- TPS 개선 방법 : 성능 문제 발생 지점 도출
    - **처리 시간이 긴** 작업을 식별 -> 실제 실행 시간 측정
    - 실행 시간을 **로그**로 남겨두기
### 수직 확장과 수평 확장
- **수직 확장** : CPU, 메모리, 디스크 등 자원 증가
    - 더 빠른 CPU, CPU 코어 증가, 메모리 확장, SSD 사용 등
    - DB 서버, API 서버 등에 적용 가능
    - 트래픽 증가 시 언젠가 문제가 재발생함
- **수평 확장** : 서버를 추가로 투입해 TPS를 증가
    - 확장 전 병목 지점을 먼저 파악
    - DB 성능 문제 -> 서버 추가 투입 -> DB에 더 많은 부하 가중
    - DB, 외부 API 성능 문제가 발생하지 않는 범위 내에서 확장
### DB 커넥션 풀
- 서버 <-> DB : **네트워크 통신**으로 연결
    - 매 요청마다 연결, 종료 시 처리량이 감소
- **커넥션 풀** : DB에 연결된 커넥션을 미리 생성 후 보관
    - DB 작업 시 풀에서 커넥션을 가져와 사용 후 반환
    - 이미 연결된 커넥션 재사용 -> 응답 시간이 감소
    - Spring Boot -> HikariCP
    - Go 언어 -> 자체 커넥션 풀 제공
- 중요 설정
    - 커넥션 풀 크기 (최소, 최대)
    - 커넥션 부재 시 최대 대기 시간
    - 커넥션 유지 시간 (최대 유휴 시간, 최대 유지 시간)
### 커넥션 풀 크기
- 미리 생성해둘 커넥션 개수
- 응답 시간, TPS를 고려하여 설정해야 함
- 최소 크기, 최대 크기를 지정
    - 트래픽이 증가할 때는 최대 크기로 확장
    - 트래픽이 적은 시간대는 최소 크기 유지
    - 트래픽이 급증하는 패턴 -> 최소 크기를 최대 크기에 맞추는 것이 좋음
- 커넥션 풀 크기 증가 -> 처리량 증가
    - DB 서버의 상태를 보고 증가
### 커넥션 대기 시간
- 커넥션을 얻기 위해 기다릴 수 있는 최대 시간
    - 대기 시간 안에 얻지 못하면 에러 발생
- 응답 시간이 중요한 서비스 -> 최대한 짧게 (0.5초 ~ 3초)
    - 빠른 에러 반환 가능
### 최대 유휴 시간, 유효성 검사, 최대 유지 시간
- 커넥션이 사용되지 않는 시간이 길어짐 -> 연결이 끊길 수 있음
- **최대 유휴 시간** : 커넥션을 풀에 유지 가능한 최대 시간
- **유효성 검사** : 커넥션을 정상적으로 사용 가능한지 확인하는 절차
    - 유효하지 않은 커넥션을 식별하고 제거
    - 실제 쿼리 실행 (```SELECT FROM dual```, ```SELECT 1```)
### 서버 캐시
- DB 서버를 확장하는 드는 비용이 큼
- 확장하지 않고도 응답 시간, 처리량을 개선 -> **캐시**
- (key,value) 형태의 데이터 저장소
- 데이터를 읽는 속도가 DB보다 빠름
- DB, 복잡한 계산 결과, 외부 API 연동 결과를 보관하여 활용
### 적중률과 삭제 규칙
- 캐시 효율성 -> 적중률로 판단
- **적중률 (Hit Rate)** : 캐시 존재 건수 / 캐시 조회 시도 건수
- 적중률이 높을수록 DB 연동 감소 -> 응답 시간, 처리량, DB 부하 감소
- 적중률 개선 방법
    - 캐시에 최대한 많이 저장
        - 메모리 용량에 한계 -> 무작정 많이 저장 불가
        - 캐시가 가득찬 경우 기존 데이터 제거
            - LRU (Least Recently Used)
            - LFU (Least Frequently Used)
            - FIFO (First In First Out)
        - 오래된 데이터는 미리 삭제하는 것이 좋음
            - 유효 시간 설정 -> 효율적인 메모리 관리
### 로컬 캐시와 리모트 캐시
- **로컬(인-메모리) 캐시** : 서버 프로세스와 동일한 메모리를 사용
    - 속도가 빠름
    - 외부 연동이 필요 없음
    ---
    - 저장할 수 있는 데이터 크기에 제한
    - 프로세스 재시작 시 캐시 데이터가 모두 삭제
        - 일시적으로 적중률 하락
- **리모트 캐시** : 별도 프로세스를 사용
    - 캐시 크기를 유연하게 조절 가능
        - **Redis** : 수평 확장 기능 제공
    - 서버 프로세스 재시작 시에도 데이터 유지 
        - 캐시 효율을 높일 수 있음
    ---
    - 네트워크 통신 필요 -> 속도가 느림
    - 별도 서버 장비, 프로세스 필요 -> 시스템 구조가 복잡
- 상황이나 용도에 맞게 로컬, 리모트 캐시를 사용
    - 데이터 규모, 변경 빈도, 응답 시간, 처리량 고려
    1. 데이터 규모가 작고 변경 빈도가 낮음 -> **로컬 캐시**
    2. 데이터 규모가 크고 배포 빈도가 높음 -> **리모트 캐시**
### 캐시 사전 적재
- 트래픽 급증 패턴 -> 캐시에 데이터를 **미리 저장**
- 캐시 적중률 -> 응답 시간, DB 부하에도 영향
    - 정보 조회 전 미리 캐시에 저장 -> 적중률 증가
### 캐시 무효화
- 유효하지 않은 데이터 -> 적절한 시점에 캐시에서 삭제
- 원본의 변경 -> 캐시 데이터도 변경, 삭제해야 됨
    - 그렇지 않으면 사용자가 잘못된 정보를 얻게 됨
- 데이터의 특성에 따라 무효화 시점을 다르게 설정
    - 민감한 데이터 -> 즉시 캐시 무효화
        - 리모트 캐시에 보관하는 것이 좋음
        - 로컬 캐시는 다른 서버의 캐시는 변경하지 않기 때문
        - 서비스 신뢰성에 영향
    - 변경에 민감하지 않고 크기가 작은 데이터 -> 유효 시간 설정
        - 변경 시차가 존재해도 서비스에 문제가 되지 않음
### 가비지 컬렉터와 메모리 사용
- **가비지 컬렉터** : 사용이 끝난 객체를 정해진 규칙에 따라 반환
    - 힙 메모리 사용량 초과, 특정 주기
    - **개발자의 메모리 관리 부담**을 줄여줌
    - 보안 이슈를 줄여좀
    - **응답 시간**에 영향을 줌 (애플리케이션 실행 중단)
- **사용 메모리, 객체 수**에 따라 GC 실행 시간 결정
    - 메모리 사용 패턴에 맞게 힙 크기 조정
- 한번에 대량 객체 생성 주의
    - 조회 범위 제한 -> 10년 치 대신 3개원 치만
    - 트래픽 규모, 메모리 크기에 맞춰 제한
- 파일 다운로드 -> 스트림 활용
    - 파일을 끊어서 읽기
### 응답 데이터 압축
- 응답 시간 : 데이터 전송 시간이 포함
    - 전송 시간 -> **네트워크 속도, 전송 데이터 크기**에 영향
- 네트워크 속도는 제어 불가 -> **전송 데이터 크기**를 제어
    - 응답 데이터를 압축
    - 압축 시 70% 이상 크기 감소 -> 전송(응답) 시간이 빨라짐
    - 클라우드 환경 -> 비용 절감 (트래픽에 비례)
    - Apache, Nginx :  압축 기능 제공
```
이미지나 zip 파일은 압축해도 효과가 적음
-> 텍스트 형식에 압축을 적용
```
### 정적 자원과 브라우저 캐시
- 서버의 응답 데이터
    - **동적 자원** : 브라우저가 요청할 때마다 바뀌는 데이터
        - 목록 HTML, 상세 JSON 응답
    - **정적 자원** : 같은 URL에 대해 같은 데이터를 응답하는 콘텐츠
        - 이미지, JS, CSS
        - 전체 트래픽에서 많은 비중 차지
- 동일한 페이지 -> 같은 데이터를 매번 다운로드 -> 트래픽(비용) 증가
    - **클라이언트 캐시** : 응답 데이터를 클라이언트가 저장
        - 로컬 캐시에 다운로드한 파일을 보관
        - 트래픽 감소 -> 네트워크 전송 비용 절감
