# 3장. 성능을 좌우하는 DB 설계와 쿼리
## 성능에 핵심인 DB
### 풀스캔
- 재택 수업으로 인한 서비스 사용자 증가
  - DB 장비의 CPU 사용률 증가
  - **풀 스캔**으로 인한 쿼리 실행 시간 증가
```
풀 스캔 : 테이블의 모든 데이터를 순차적으로 읽는 것
- WHERE 조건절에 해당하는 인덱스가 없는 경우 발생
- 풀 스캔이 더 빠른 경우 발생 
- 데이터 개수가 증가할 경우 풀 스캔으로 인한 성능 문제 발생
```
## 조회 트래픽을 고려한 인덱스 설계
### 인덱스
- 일반적인 조회 시스템 : 조회 기능의 비율이 높음 (ex. 게시판)
  - 게시판별 특성 (인기 커뮤니티, 회사 공지사항)
- DB 테이블 설계시 조회 기능, 트래픽 규모를 고려
  - ex. 카테고리별 게시글 목록을 조회하는 기능
    1. 회사 공지 게시판 : 규모가 작아 인덱스를 추가할 필요가 없음
    2. 인기 커뮤니티 게시판 : 수천만 건의 데이터 조회 -> 풀스캔 시 CPU 사용률 증가
        - **조회 패턴을 기준으로 인덱스를 설계해야 함**
### 단일 인덱스와 복합 인덱스
```
select * from activityLog 
where userId = 123 and activityDate = '2024-07-31'
order by activityDatetime desc
```
- 단일 인덱스 : userId만 인덱스로 사용
- 복합 인덱스 : (userId, activityDate)를 인덱스로 사용
- 사용자가 가질 수 있는 데이터의 양을 고려
  - 사용자당 1주일 평균 활동 데이터 = 5건 -> 단일 인덱스만 사용해도 됨
  - 활동성이 좋을 경우 (사용자당 수만 건) -> 컬럼 조합 복합 인덱스 사용을 고려
```
select activityDate, activityType, count(activityType)
from activityLog
where activityDate = '2024-07-28'
group by activityType;
```
- 풀 스캔 방지를 위해선 `activityDate` 컬럼을 인덱스로 사용
  - `activityType` 컬럼을 인덱스로 사용할 것인가?
  - 쿼리 실행 빈도와 실행 시간을 검토해서 포함 여부를 결정
  1. `activityDate`만 -> 해당 일자 데이터를 모두 조회 -> 수만 건인 경우 오래 걸림
     - 하루에 한번만 실행한다면 상관 x
  2. 하루에 수백만 건의 데이터가 쌓이는 경우 -> 복합 인덱스 사용을 고려
### 선택도를 고려한 인덱스 컬럼 선택
- 인덱스 생성은 **선택도가 높은** 컬럼을 골라야 함
  - 선택도 : 특정 컬럼의 고유한 값 비율
    - 선택도가 높으면 해당 컬럼의 고유한 값이 많음 -> 조회 효율이 높아짐
- 선택도가 낮아도 사용하기 좋은 경우 **ex. 작업 큐**
```
create table jobqueue (
    jobId varchar(16) not null primary key,
    status char(1) not null,
    ...
);
```
- `status` 컬럼 : W, P, C 값을 가짐 -> 선택도가 낮음
  - 작업 큐가 처리하는 코드 : `status`가 W인 데이터
  - `status` 컬럼에 인덱스를 걸어야 풀 스캔이 발생하지 않음
### 커버링 인덱스 활용하기
- **커버링 인덱스**: 특정 쿼리를 실행하는데 필요한 컬럼을 모두 포함하는 인덱스
    - 쿼리 효율을 높일 수 있음
### 인덱스는 필요한 만큼만 만들기
```
select * from activityLog
where userId = 123 and activityDate = '2024-07-31`
order by activityDatetime desc;

select * from activityLog
where userId = 123 and activityDate = '2024-07-31' and activityType = 'BUY'
order by activityDatetime desc;
```
- 사용할 수 있는 복합 인덱스
  1. (userId, activityDate)
  2. (userId, activityDate, activityType)
  - 2번의 효과가 좋으려면 -> 사용자가 하루에 만드는 데이터 개수가 조회 성능에 영향을 줄 정도로 많아야 함
- 효과가 적은 인덱스 추가 -> 성능이 나빠짐
  - 데이터 추가, 변경, 삭제 시 인덱스 관리에 따른 비용 증가
  - 인덱스 자체도 데이터 : 메모리, 디스크 사용량이 함께 증가
- 새로 추가하는 쿼리가 인덱스를 사용하지 않을 경우 -> 요구사항 변경 검토
  - 기존에 존재하는 인덱스를 활용할 수 있게
```
create table reservation (
    id bigint not null primary eky,
    name varchar(30) not null,
    reserveDate date not null,
    state char(2) not null,
    regDt timestamp not null
);
create index idxRdate ON reservation (reserveDate);
```
- 예약자 이름으로 조회하는 기능 -> name 컬럼 비교
  - **풀 스캔** 발생
  - 특정 일자에 예약한 예약자 이름으로 조회하도록 변경
    - 인덱스를 사용 -> 풀스캔 없이 데이터 조회 가능
## 몇 가지 조회 성능 개선 방법
### 미리 집계하기
ex. 설문조사 기능
- `count`, `sum`과 같은 집계 쿼리 조회 시 데이터가 많으면 성능 문제 발생
  - 집계 데이터를 미리 계산해서 별도 컬럼에 저장
  - 테이블에 답변자 수, 좋아요 수를 저장할 컬럼 지정
  - 답변 생성 혹은 좋아요를 누를 시 해당 컬럼값을 증가하는 방법
  - 해당 방법 사용 시 집계를 위한 서브쿼리를 실행할 필요 x
```
집계 정보 추가로 인한 데이터 중복 (정규화 위반)
- 불일치를 감수해도 집계용 컬럼을 추가하는 것이 합리적
- 서비스에 심각한 문제가 되지 않음
- 정확한 값은 언제든지 구할 수 있음

동시성 문제 처리
- 원자적 처리를 검증해야 함
```
### 페이지 기준 목록 조회 대신 ID 기준 목록 조회 방식 사용하기
- 게시글 데이터 10만 개 -> 10개씩 보여주면 1만 개의 페이지
```
** 첫 번째 페이지
select id, subject, writer, regdt
from article
order by id desc
limit 10 offset 0;

** 1만 번째 페이지
select id, subject, writer, regdt
from article
order by id desc
limit 10 offset 99990;
```
- 99991번째 id를 바로 조회하지 못함 -> 99990개의 id를 세고 10개 데이터 조회
    - 그만큼 실행 시간이 증가
```
select id, subject, writer, regdt
from article
where deleted = false
order by id desc
limit 10 offset 99990;
```
- `deleted` 컬럼은 인덱스에 포함 x 
  - 각 행의 `deleted` 값을 읽어야 함
  - false 데이터르 1만 개 세기 위해 데이터를 1만 개 이상 조회해야 함 (true도 있음)
  - `deleted` 컬럼에 인덱스를 걸어도 오프셋만큼 데이터를 세야 함
- **특정 ID를 기준**으로 조회
```
select * from article
where deleted = false
order by id desc
limit 10
-> 마지막 데이터 id : 9985

select * from article
where id < 9985 and deleted = false
order by id desc
limit 10;
```
- id는 인덱스 -> 9985보다 작은 id 9984를 바로 찾을 수 있음
  - 오프셋만큼 데이터를 세는 시간 생략 -> 실행 시간이 빠름
- 모바일 화면 : 스크롤을 통해 다음 데이터를 조회
  - **ID 기준 조회**가 더 효과적
- 다음 데이터가 존재하는지 프론트에게 알려주고 싶음
  - **11개**를 조회하고, 11번째 데이터가 존재 시 다음에 읽을 데이터가 존재한다고 판단
### 조회 범위를 시간 기준으로 제한하기
- 조회 성능 개선 방법 -> 조회 범위를 **시간 기준**으로 제한
- ex. 뉴스 기사 목록
```
select title, ...
from news
where regdt >= '2024-08-09 00:00:00' and regdt < '2024-08-10 00:00:00'
order by regdt desc
limit 100;
->  regdt 컬럼에 인덱스 추가 시 성능 문제 x
```
- 페이지 기준, ID 기준 조회보다 쿼리가 단순하고 성능 문제 발생 x
- 조회 범위 제한 방법 -> **최신 데이터**만 조회
  - ex. 매달 점검 결과 제공
  - 단일 쿼리로 단순화 가능
  - **캐시와의 시너지** 증가 (최신 데이터가 적재될 확률이 높음)
### 전체 개수 세지 않기
- 목록 표시 기능 -> 전체 개수를 표시하는 경우가 많음
  - count 함수 사용
  - 데이터가 증가할 경우 count 실행 시간 증가
- 실행 시간 유지 방법 -> 데이터 증가 속도를 늦추기
  - 과거 데이터 삭제 (ex. 로그인 내역)
```
DELETE를 사용한 데이터 삭제
- 단편화 발생 -> 디스크 I/O 증가, 디스크 낭비
-> 최적화 작업을 통한 데이터 재배치
```
### DB 장비 확장하기
DB 부하로 인한 성능 문제 발생 시 해결 방법
1. DB 장비의 수직적 확장
   - 더 빠른 CPU, 더 많은 CPU
2. DB 장비의 수평적 확장
   - 조회 트래픽 비중이 높은 서비스 -> **주 DB - 복제 DB** 구조 사용 권장
     - 변경 쿼리 -> 주 DB
     - 조회 쿼리 -> 복제 DB
     - 트래픽 증가 시 복제 DB 추가
### 별도 캐시 서버 구성하기
- 트래픽 증가 시 DB만으로 모든 트래픽을 처리하지 못할 수 있음
  - 별도 **캐시 서버**를 구성
  - DB 확장 대비 적은 비용으로 더 많은 트래픽 처리 가능
  - 코드를 수정해야 하는 단점이 있음
## 알아두면 좋을 몇 가지 주의 사항
### 쿼리 타임아웃
- 응답 지연으로 인한 재시도 -> 서버 부하 가중
  - 쿼리 실행 시간을 제한 (타임아웃 설정)
    - 이전 요청을 일찍 정상 종료 처리
  - 서비스의 특성에 따라 다르게 설정
    - 블로그 조회 -> 짧게 설정
    - 상품 결제 기능 -> 길게 설정 (결제 처리 중 타임아웃 발생을 방지)
### 상태 변경 기능은 복제 DB에서 조회하지 않기
- 변경 쿼리 -> 주 DB, 조회 쿼리 -> 복제 DB
- 모든 SELECT 쿼리를 복제 DB에서 실행하는 경우
  1. 주 DB, 복제 DB 사이의 순간적인 데이터 불일치
  2. 트랜잭션 문제 발생
    - 데이터 복제는 트랜잭션 커밋 시점에 발생
    - 트랜잭션 중 복제 DB 조회 시 데이터 불일치 발생
- 변경 대상 데이터 조회 시 주 DB에서 SELECT 쿼리를 실행하는 것을 권장
### 배치 쿼리 실행 시간 증가
- **배치 프로그램**: 데이터 일괄 조회, 집계, 생성 작업 수행
  - ex. 일별 회원 통계, 사용 내역 기준 요금 계산
  - group by -> count, sum으로 집계
- 데이터 증가에 따라 쿼리 실행 시간이 기하급수적으로 증가
  - 지속적으로 쿼리 실행 시간을 추적
  - 문제가 되는 쿼리를 발견 후 해결
    1. DB 장비 사양 높이기
    2. 커버링 인덱스 활용
       - 집계 대상에 인덱스 포함 -> 인덱스만 스캔
    3. 데이터를 일정 크기로 나눠서 처리
       - ex. 한 달간 통계 데이터 추출 -> 일별로 처리 후 합쳐서 전체 결과 생성
          1. 마지막 반영 시간을 구하기
          2. 마지막 반영 시간 ~ 간격 시간 동안의 데이터 집계
          3. 집계 데이터를 통계에 반영
### 타입이 다른 컬럼 조인 주의
- 조인 시 타입 변환이 발생하면, 해당 컬럼 인덱스를 온전히 사용하지 못함
  - 비교 대상 컬럼의 타입을 미리 맞춰놓아야 함
### 테이블 변경은 신중하게
- 데이터가 많은 테이블
  - 새로운 칼럼 추가 및 기존 열거 타입 컬럼 변경 시 주의해야 함
  - MySQL -> 테이블 변경 시 새 테이블 생성, 원 테이블 복제 후 대체
    - 복사 시간만큼 서비스가 중지
    - 서비스 중단 후 변경하는 것이 안정적
### DB 최대 연결 개수
- DB 서버 자원에는 여유가 있지만 DB 연결이 안된다면 -> 최대 연결 개수 확인
  - 필요 시 최대 연결 개수 증가
  - DB 서버 CPU 사용률이 높다면 연결 개수를 늘리면 안됨
    - DB 부하 증가 및 성능 저하 발생
    - **캐시 서버 구성** 및 **쿼리 튜닝**을 통해 DB 부하를 낮춤
## 실패와 트랜잭션 고려하기
### 트랜잭션
- 트랜잭션을 고려하지 않으면 데이터 일관성에 문제 발생 
  - 트랜잭션의 시작과 종료 경계를 명확히 설정
  - 일부 기능에서 오류 발생 시 전체 트랜잭션 롤백
  - BUT 오류가 발생해도 커밋해야 하는 경우가 존재
    - ex. 회원 가입 시 축하 메일 발송 -> 메일 발송 시 오류가 났다 해서 회원 가입을 취소해서는 안됨
    - 메일 발송 오류는 별도로 처리해야 함
